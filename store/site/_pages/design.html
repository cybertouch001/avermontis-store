For the owner

System design

How the store works now that it has a real backend, and how to grow it from 2 to 200 users without over-building. Honest summary: static pages on a global CDN + one server function + a SQL database (Cloudflare D1). Customer accounts, saved orders, sign-in history and the owner dashboard are live. Online payment (Razorpay) is the next step.

2. How data moves

  1. Shopper opens a page → CDN sends HTML, CSS, JS, products.js and WebP images.
  2. Cart = {product id: quantity} in the browser. Totals on screen are always recalculated from products.js.
  3. Sign up / sign in → POST /api/auth/* → server checks the password against a PBKDF2 hash, writes a row to login_history (success or failure, IP, device), and sets an HttpOnly session cookie. JavaScript never sees the session.
  4. "Place order" → browser sends only items [id, qty] + address → server re-prices from products.js, validates, links the order to the signed-in account (from the cookie, never from the request body) and saves it in orders + order_items.
  5. My account → /api/account/* returns only rows where user_id = the signed-in user.
  6. Owner opens /admin → owner session cookie → /api/admin/* reads everything; status changes write back to orders.

4. What breaks first at 10× traffic

  1. The owner's manual work, not the servers. Every order now lands in /admin, but confirming COD orders by phone and shipping by hand will take hours at 10×. Fix: courier integration (Shiprocket) + order notifications.
  2. Cash on Delivery risk. More COD = more fake orders and returns-to-origin. Fix: Razorpay + phone confirmation for big COD orders.
  3. No stock tracking. Two people can buy the last unit. Fix: a stock column + decrement inside the order batch.
  4. Editing products.js by hand. Fine for 5 products. Fix at ~30 products: products table + edit form in /admin.
  5. Database limits. D1's free tier is ample for 200 users (millions of reads/day). Watch the admin "All orders" list: add pagination filters by date when it passes a few thousand rows (indexes already exist).

Backup and restore

  1. Owner, any time: /admin → Orders → "Export orders CSV" and Login history → "Export login history CSV" (save to Google Drive).
  2. Full backup: D1 keeps 30 days of point-in-time history (Time Travel) — ask Tab to restore to a moment before a mistake.
  3. Restore of a CSV or SQL dump goes into a fresh database, checked, then switched over.

8. Security checklist

  • Prices & money: server re-prices every order from products.js; browser prices, totals and user ids in the request are ignored.
  • Passwords: PBKDF2-SHA256, 100,000 iterations, random 16-byte salt per password; never stored or logged in plain text. Same error for unknown email and wrong password.
  • Sessions: random 256-bit token in an HttpOnly, Secure, SameSite=Lax cookie; only its SHA-256 is stored. Customer 30 days, owner 12 hours. Sign-out deletes the session.
  • Owner access: no password in the code or in chat; one-time /admin/setup guarded by the database primary key (works exactly once, even under a race).
  • Rate limits (top of _worker.js): login + signup 10 per 2 min per IP; owner login 10 per 2 min; orders 5 per 10 min; other writes 120/min. Answer: 429 + Retry-After + "try again in N seconds".
  • Injection: every SQL query uses bound parameters; all output escaped in the page (XSS); CSV export neutralises spreadsheet formulas.
  • Headers: Content-Security-Policy (own scripts only, no framing), HSTS, X-Frame-Options DENY, nosniff, Referrer-Policy, Permissions-Policy; account and admin pages are no-store + noindex.
  • OWASP Top 10: A01 access control ✓ (server checks), A02 crypto ✓ (PBKDF2, HTTPS only), A03 injection ✓, A04 design ✓ (server-side rules), A05 misconfig ✓ (headers, no stack traces), A06 outdated packages ✓ (no packages in production), A07 auth ✓ (rate limits, hashed sessions), A08 integrity ✓ (no third-party scripts), A09 logging ◐ (sign-ins logged; error alerts are a next step), A10 SSRF ✓ (no server-side fetch of user URLs).

10. The 5 best next steps (2 → 200 users)

  1. Razorpay — online payment with webhook verification; the orders table is ready (add payment_status).
  2. Products in the database — edit products, prices and stock from /admin without touching code (orders + status already live).
  3. Shipping partner (e.g. Shiprocket) — pincode serviceability check at checkout and automatic tracking links.
  4. Password reset by email + saved addresses — accounts and order history are live; add reset links and verified reviews.
  5. Monitoring — uptime check every minute, error tracking with alerts to the store email, and a weekly look at conversion (visits → carts → orders).

Watch these numbers to know when to do the next step: orders per day (>5/day → courier integration), COD cancellations (>10% → push online payment), time spent editing products (>30 min/week → database).
